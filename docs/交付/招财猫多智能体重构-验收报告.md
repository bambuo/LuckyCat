## 五、真实运行发现的缺陷（单测全绿也抓不到的）

| 缺陷 | 影响 | 修复 |
| --- | --- | --- |
| 框架 `RunAsync<T>` 强制 `response_format=json_schema` | DeepSeek 直接 400，每个阶段第一步即失败 | 改纯文本 + `JsonPayload.Extract` + 严格解析，契约仍由提示词与阶段校验兜住 |
| Gate 的 K 线成交量整列 0 | 模型判定「量能不可验证」而一律 `hold` | 成交量优先 `Volumes`，缺失时回退 `SharedKline.Volume`；真实值为 154 万等 |
| `confidence` 用 0–100 写 | 下游 ×100 变成 7600 | 提示词钉死 0–1；交易员阶段拦越界值（FLOW-07 重试一次后 fail-closed） |

结论：这三类问题只有接真实提供商/交易所才会暴露；本报告的验收以真实链路为准，不以测试数代替。

## 六、验收边界与遗留

| # | 项 | 说明 |
| --- | --- | --- |
| 1 | 前端自动化仅覆盖纯函数 | `web/tests/sse.test.ts`（`bun test`）覆盖 SSE 帧解析与事件名清单；页面交互、SSE 实时刷新等仍以人工浏览器验收为准 |
| 2 | 无鉴权、仅本机 | 设计边界：应用监听 `localhost`，不做公网暴露；远程使用需先加认证与 TLS |
| 3 | 外部消息源无 SLA | 单源失败只在 `get_news` 的 warnings 记「源 X 缺席」，不影响周期；源站改版需按 LC-STD-06 维护端点 |
| 4 | 试运行不可交易 | 设计行为：合成账户 + 归属硬闸，执行阶段的下单/账户请求按 API-06 被拒绝，UI 以正常结果呈现 |
